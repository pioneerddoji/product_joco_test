# 03. 시행착오와 문제 해결

이 문서는 커밋에서 직접 확인되는 구조 변화와 현재 환경에서 재현된 진단 사례를 바탕으로 작성했습니다. 당시의 대화 기록이 없는 항목은 “실패했다”고 단정하지 않고, **이 프로젝트에서 실제로 마주칠 수 있는 위험과 해결 원칙**으로 표현합니다.

## 1. 한 파일이 너무 커지는 문제

### 관찰

초기에는 `index.html` 하나에 화면, 스타일, 동작이 모두 있었습니다. 테마, 문의, 댓글, 광고가 이어서 추가되면서 파일의 책임이 커졌고, `c935952`에서 공통 CSS와 JavaScript, 안내 페이지, 검증 스크립트로 크게 재구성되었습니다.

### 배운 점

처음부터 완벽한 구조를 만들 필요는 없습니다. 하지만 다음 신호가 보이면 분리해야 합니다.

- 같은 스타일이나 스크립트를 여러 위치에서 고친다.
- 본문보다 외부 위젯 코드가 더 눈에 띈다.
- 정책·소개·가이드가 한 페이지를 지나치게 길게 만든다.
- 한 기능을 수정했는데 다른 기능이 깨졌는지 확인하기 어렵다.

### 적용한 해결

- `styles.css`: 공통 시각 규칙
- `app.js`: 공통 동작
- 목적별 HTML 페이지
- `scripts/verify.mjs`: 반복 확인의 자동화

## 2. 배포 URL 기준이 달라지는 문제

### 관찰

중간 검증 스크립트는 기준 URL로 `https://pioneerddoji.github.io/product_joco_test/`를 사용했고, 현재 스크립트는 `https://pioneerddoji.github.io/`를 사용합니다. 로컬 Git에는 제품 저장소와 사용자 Pages 저장소, 두 원격이 연결되어 있습니다. GitHub API상 제품 저장소 자체의 Pages 주소도 `/product_joco_test/` 경로로 존재합니다.

### 위험

사이트는 열리더라도 canonical, sitemap, robots가 다른 주소를 가리킬 수 있습니다. 분석 데이터가 나뉘거나 검색 엔진이 중복 페이지로 판단할 수 있습니다.

### 해결 원칙

먼저 대표 배포 주소를 하나 정하고 아래 항목을 한꺼번에 맞춥니다.

```text
GitHub Pages 설정
→ canonical
→ sitemap.xml
→ robots.txt
→ JSON-LD url
→ Google Search Console
→ 분석 도구 속성/필터
→ Disqus page.url
```

두 주소를 모두 운영해야 한다면 한쪽을 대표 주소로 정하고 다른 쪽에는 리디렉션 또는 명확한 canonical 전략이 필요합니다.

## 3. 한글이 깨져 보이는 문제: 파일 손상인가, 출력 문제인가

### 재현된 현상

PowerShell에서 `Get-Content -Raw`로 UTF-8 HTML을 읽었을 때 한글이 깨져 보였지만, `Get-Content -Raw -Encoding utf8`로 읽자 정상적으로 표시되었습니다. Node.js도 같은 파일을 UTF-8로 정상 처리했고 자동 검증을 통과했습니다.

### 잘못된 대응

화면에 깨져 보인다는 이유만으로 파일 전체를 다시 저장하면 정상 파일을 실제로 손상시킬 수 있습니다.

### 안전한 진단 순서

1. HTML에 `<meta charset="utf-8">`가 있는지 확인한다.
2. 읽기 명령에 UTF-8을 명시한다.
3. 브라우저와 다른 도구에서도 같은 증상인지 비교한다.
4. Git diff로 실제 바이트 변경이 있는지 본다.
5. 원인이 확인되기 전에는 일괄 인코딩 변환을 하지 않는다.

```powershell
Get-Content -Raw -Encoding utf8 .\index.html
```

핵심 교훈은 **표시 계층의 오류와 저장 데이터의 오류를 분리해서 진단하라**는 것입니다.

## 4. 외부 서비스는 코드 삽입만으로 완료되지 않는다

### 관찰

문의, 댓글, 광고, 분석 기능이 각각 별도 커밋으로 추가되었습니다. Clarity 추가 때에는 개인정보처리방침도 함께 보강되었습니다.

### 흔한 누락

- Formspree 폼은 보이지만 수신 이메일 인증이 안 됨
- Disqus shortname은 맞지만 사이트 URL 매핑이 틀림
- AdSense 코드와 `ads.txt`는 있지만 계정 심사가 끝나지 않음
- 분석 스크립트는 있으나 동의·차단 정책을 검토하지 않음
- 홈에만 스크립트를 넣고 하위 페이지에서 누락

### 해결 원칙

외부 서비스마다 아래 세 묶음을 같이 관리합니다.

1. **코드:** 로더, 계정 식별자, 페이지 식별자
2. **운영:** 대시보드 설정, 권한, 알림, 실제 데이터 수신
3. **고지:** 개인정보, 쿠키, 댓글 정책, 서비스 한계

## 5. 페이지가 늘 때 공통 코드가 누락되는 문제

### 관찰

분석 도구는 모든 HTML 페이지에 반복 삽입되어 있습니다. 현재 검증 스크립트는 각 페이지마다 로더와 설정 코드가 정확히 한 번 있는지 검사합니다.

### 장점과 한계

검증 덕분에 누락과 중복을 잡을 수 있습니다. 그러나 페이지를 새로 만들고 `pages` 배열에 등록하지 않으면 그 페이지는 검사 대상이 아닙니다.

### 개선 아이디어

- `*.html`을 자동 탐색해 검사한다.
- 공통 `<head>`, header, footer를 템플릿으로 생성한다.
- 페이지별 예외를 설정 파일에 명시한다.
- CI에서 검증 스크립트를 자동 실행한다.

## 6. 자동 검증이 주는 거짓 안도감

### 관찰

현재 검증은 성공합니다. 하지만 HTML을 완전한 DOM 파서로 분석하지 않고 일부는 정규식으로 확인합니다. JavaScript 동작도 간단한 가상 객체에서 시험합니다.

### 통과해도 남는 질문

- 모바일 화면에서 메뉴가 겹치지 않는가?
- 키보드만으로 모든 기능을 쓸 수 있는가?
- 색 대비가 충분한가?
- 문의가 실제로 도착하는가?
- 광고와 분석 요청이 운영 대시보드에 잡히는가?
- 배포된 파일이 최신 커밋인가?

### 해결 원칙

검증을 세 층으로 나눕니다.

| 층 | 예시 | 현재 상태 |
|---|---|---|
| 정적 검사 | 링크, 메타, 중복 ID | 자동화됨 |
| 기능 검사 | 번호 생성, 테마 | 일부 자동화됨 |
| 운영 검사 | 실배포, 외부 서비스, 실제 기기 | 수동 체크 필요 |

## 7. 확률 도구를 예측 도구로 오해시키는 문제

번호 생성기는 편의 도구이지 당첨 예측기가 아닙니다. 이 프로젝트는 조합 수와 무작위성 콘텐츠, 책임 있는 사용 안내를 추가했습니다.

교육할 때는 다음 문장을 분명히 전달합니다.

- 과거에 자주 나온 번호가 다음 추첨에서 더 유리하지 않다.
- 모양이 예쁜 조합과 불규칙한 조합의 추첨 확률은 같다.
- 오름차순 정렬은 표시만 바꾸며 확률을 바꾸지 않는다.
- 생성 결과는 구매 권유나 수익 보장이 아니다.

## 8. 다음 작업에서 개선할 우선순위

1. 대표 배포 URL과 두 Pages 원격의 역할을 문서화한다.
2. 새 HTML 파일도 자동 발견하는 검증으로 바꾼다.
3. 실제 브라우저 기반 접근성·반응형 테스트를 추가한다.
4. 외부 서비스의 운영 확인일과 담당자를 기록한다.
5. 공통 HTML 중복이 커지면 정적 사이트 생성기를 검토한다.
