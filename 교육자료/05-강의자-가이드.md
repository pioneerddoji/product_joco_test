# 05. 제3자 교육용 강의안

## 강의 개요

- 제목: 작은 웹 기능을 공개 가능한 정적 서비스로 키우기
- 대상: HTML/CSS/JavaScript 기초를 배운 입문자
- 권장 시간: 120분
- 방식: 저장소 탐색 30분 + 코드 해설 35분 + 실습 35분 + 회고 20분
- 핵심 메시지: **서비스 완성도는 기능 수가 아니라 기능·설명·정책·검증·운영의 연결에서 나온다.**

## 학습 목표

수강생은 강의가 끝난 뒤 다음을 할 수 있어야 합니다.

1. Git 커밋 기록으로 프로젝트의 의사결정 흐름을 설명한다.
2. 번호 생성 알고리즘의 조건과 한계를 설명한다.
3. 정적 사이트에 외부 서비스를 연결할 때 생기는 운영 책임을 열거한다.
4. canonical, sitemap, robots의 URL 기준을 일치시킨다.
5. 자동 검증과 수동 운영 검증의 차이를 설명한다.

## 수업 전 준비

- 저장소를 내려받고 `node scripts/verify.mjs`가 통과하는지 확인합니다.
- 인터넷이 불안정할 경우를 대비해 외부 위젯은 화면 캡처 또는 설명으로 대체합니다.
- 실제 문의 폼에 수강생이 개인정보를 입력하지 않도록 안내합니다.
- 광고·분석 계정의 대시보드는 개인 정보가 보이지 않는 데모 화면만 사용합니다.
- 도박을 권장하는 수업으로 오해되지 않도록 확률과 책임 있는 사용 안내를 먼저 준비합니다.

## 120분 진행안

### 0~10분 — 문제 제시

화면에 번호 생성기만 보여 주고 질문합니다.

> “이 버튼이 잘 작동하면 공개 서비스가 완성된 것일까요?”

예상 답변을 기능, 디자인, 신뢰, 법·정책, 배포, 측정으로 묶어 칠판에 적습니다.

### 10~30분 — 커밋 타임라인 읽기

11개 커밋을 세 단계로 분류하게 합니다.

- 기능 검증
- 사용자 상호작용
- 콘텐츠·신뢰·운영

강의자는 `c935952`의 변경량이 큰 이유를 묻습니다. 정답 하나를 찾기보다 “기능이 늘어난 뒤 구조를 다시 잡은 전환점”이라는 관찰을 끌어냅니다.

### 30~50분 — 핵심 JavaScript

`generateSet`, `getColor`, 테마 토글을 순서대로 설명합니다.

확인 질문:

- `+ 1`이 없으면 어떤 숫자 범위가 되는가?
- `includes` 검사를 빼면 어떤 문제가 생기는가?
- 정렬이 확률을 바꾸는가?
- `localStorage`에는 어떤 정보가 저장되는가?

### 50~65분 — 정적 사이트의 구조

파일 트리를 보여 주고 각 파일의 책임을 수강생에게 연결하게 합니다. `privacy.html`과 `terms.html`을 “형식적인 페이지”로 소개하지 말고, 외부 서비스 연결과 함께 바뀌는 운영 문서로 설명합니다.

### 65~80분 — 외부 서비스와 데이터 흐름

다음 흐름을 그립니다.

```text
방문자 브라우저 → GitHub Pages의 정적 파일
                ├→ Formspree: 문의 내용
                ├→ Disqus: 댓글·계정/기기 정보
                ├→ Google: 광고·방문 측정
                └→ Microsoft: 사용 흐름 분석
```

질문:

> “서버를 직접 만들지 않았는데도 개인정보 관련 설명이 필요한 이유는 무엇일까요?”

### 80~100분 — 테스트를 일부러 깨뜨리는 실습

2~3명씩 조를 만들어 각 조에 다른 오류를 줍니다.

- 없는 내부 링크
- 중복 title
- 분석 스크립트 중복
- 번호 범위 오류

검증 스크립트가 잡는지 확인하고, 잡지 못하면 어떤 검사가 필요한지 제안하게 합니다. 실습 후 변경은 반드시 되돌립니다.

### 100~112분 — URL 시행착오 토론

사용자 Pages 주소와 프로젝트 Pages 주소를 비교합니다.

```text
https://name.github.io/
https://name.github.io/repository/
```

canonical만 바꿨을 때 놓치기 쉬운 파일과 서비스 목록을 팀별로 작성하게 합니다.

### 112~120분 — 회고

각자 아래 세 문장을 완성합니다.

- 오늘 새롭게 알게 된 것은 ______이다.
- 자동화할 수 있는 것은 ______이다.
- 사람이 직접 확인해야 하는 것은 ______이다.

## 시연 순서

1. 번호 5세트 생성
2. 다크 모드 전환 후 새로고침
3. `app.js`의 알고리즘 읽기
4. `verify.mjs` 실행
5. 내부 링크를 임시로 깨뜨려 실패 확인
6. Git log로 기능의 성장 순서 확인
7. 개인정보처리방침에서 외부 서비스 항목 확인

## 평가 기준표

| 항목 | 0점 | 1점 | 2점 |
|---|---|---|---|
| 기능 이해 | 설명 불가 | 동작만 설명 | 조건과 한계까지 설명 |
| 구조 이해 | 파일 나열 | 역할 설명 | 변경 시 연쇄 영향 설명 |
| URL 이해 | 구분 못함 | 두 유형 구분 | 관련 설정을 일괄 점검 |
| 검증 이해 | 통과 여부만 봄 | 검사 항목 설명 | 자동·수동 경계를 설명 |
| 운영 책임 | 고려 없음 | 외부 서비스 인지 | 정책·데이터·대체 흐름 제안 |

총 7점 이상이면 학습 목표를 달성한 것으로 봅니다.

## 강의자가 피해야 할 표현

- “이 번호는 당첨 확률이 높습니다.”
- “검증 스크립트가 통과했으니 버그가 없습니다.”
- “GitHub Pages에 올렸으니 SEO가 끝났습니다.”
- “외부 서비스가 처리하므로 개인정보는 신경 쓰지 않아도 됩니다.”
- “측정 ID가 공개되어 있으니 모든 키를 저장소에 넣어도 됩니다.”

## 예상 질문과 답변

### React를 쓰면 더 좋은가요?

현재 규모에서는 필수는 아닙니다. 상호작용과 공유 상태가 복잡해지거나 컴포넌트 재사용이 중요해질 때 검토합니다. 콘텐츠 페이지 중복만 문제라면 정적 사이트 생성기가 더 작은 해법일 수 있습니다.

### `Math.random()`은 정말 무작위인가요?

의사난수입니다. 일반적인 번호 제안 UI에는 사용할 수 있지만 보안·법적 추첨 용도로 쓰면 안 됩니다. 어느 조합도 미래 당첨을 더 잘 예측하지 않습니다.

### 광고 코드를 넣으면 바로 광고가 나오나요?

아닙니다. 사이트와 계정 심사, 정책 준수, `ads.txt`, 콘텐츠 상태, 광고 게재 가능 여부가 별도로 확인되어야 합니다.

### 테스트가 왜 브라우저 없이 동작하나요?

필요한 DOM 동작만 흉내 낸 작은 객체를 만들어 `app.js`를 실행하기 때문입니다. 빠르지만 실제 브라우저의 모든 동작을 재현하지는 못합니다.
