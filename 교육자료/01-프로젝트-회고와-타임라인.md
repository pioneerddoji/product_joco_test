# 01. 프로젝트 회고와 타임라인

## 1. 프로젝트의 출발점과 도착점

출발점은 로또 번호 6개를 뽑아 주는 단일 HTML 페이지였습니다. 도착점은 번호 생성 기능뿐 아니라 확률 학습 콘텐츠, 사이트 소개와 정책 문서, 문의·댓글, 검색 엔진용 파일, 광고 및 분석 도구, 자동 검증을 갖춘 정적 콘텐츠 사이트입니다.

이 변화에서 가장 중요한 교훈은 **기능을 추가하는 것과 서비스를 완성하는 것은 다르다**는 점입니다. 번호 생성 버튼은 빠르게 만들 수 있지만, 공개 서비스에는 설명, 한계 고지, 접근성, 개인정보 안내, 검색 노출, 운영 점검이 함께 필요합니다.

## 3. 세 단계로 다시 묶어 보기

### 단계 A — 기능 검증

첫 커밋은 한 파일 안에 HTML, CSS, JavaScript를 모두 넣었습니다. 유지보수성은 낮지만 아이디어 검증에는 빠릅니다. 이 단계의 질문은 하나입니다.

> 사용자가 버튼을 눌렀을 때 기대한 번호 묶음이 나오는가?

### 단계 B — 사용자 경험과 상호작용

테마, 문의, 댓글을 차례로 넣었습니다. 여기서부터 사이트는 “나 혼자 쓰는 도구”에서 “방문자와 관계를 맺는 서비스”로 변합니다. 동시에 외부 의존성, 개인정보, 스팸, 운영 책임이 생깁니다.

### 단계 C — 콘텐츠·신뢰·운영 체계

`c935952`는 가장 큰 전환점입니다. `styles.css`, `app.js`, 여러 안내 페이지, `robots.txt`, `sitemap.xml`, 검증 스크립트가 한 번에 들어왔습니다. 이후 확률 콘텐츠와 분석 도구가 보강되었습니다.

이 단계의 질문은 기능보다 넓습니다.

- 이 사이트가 무엇인지 검색 엔진과 방문자가 이해할 수 있는가?
- 확률에 대한 오해를 줄이는가?
- 외부 서비스 사용 사실과 데이터 처리를 알리는가?
- 페이지가 늘어도 공통 기능을 한 곳에서 관리할 수 있는가?
- 배포 전에 반복 점검할 수 있는가?

## 4. 현재 구조가 보여 주는 설계 판단

### 프레임워크를 쓰지 않은 선택

현재 사이트는 HTML/CSS/JavaScript만으로 동작합니다. 콘텐츠와 상호작용이 비교적 단순하고 서버 상태가 없기 때문에 합리적인 선택입니다. 설치와 빌드 과정이 없어 GitHub Pages에 바로 배포할 수 있습니다.

반면 페이지마다 헤더, 푸터, 분석 스크립트가 중복됩니다. 페이지가 더 늘어나면 템플릿 엔진이나 정적 사이트 생성기를 검토할 시점입니다.

### 외부 서비스를 조합한 선택

문의, 댓글, 광고, 분석을 직접 서버로 구현하지 않고 전문 서비스에 맡겼습니다. 개발 속도는 빨라지지만 서비스 정책, 쿠키, 장애, 차단 확장 프로그램, 지역별 규정의 영향을 받습니다.

### 교육 콘텐츠를 추가한 선택

번호를 생성하는 기능만 제공하면 사용자가 확률을 오해할 수 있습니다. 조합 수, 독립 시행, 무작위성 설명을 별도 페이지로 확장한 것은 서비스 책임과 콘텐츠 깊이를 동시에 높입니다.

## 5. 이번 프로젝트에서 얻을 수 있는 회고 문장

- 처음에는 한 파일이 빠르지만, 기능이 검증되면 역할별 파일로 분리해야 한다.
- 외부 위젯 한 줄을 추가하면 정책 문서와 검증 항목도 함께 바뀌어야 한다.
- 광고를 붙이는 일은 스크립트 삽입으로 끝나지 않고 콘텐츠 품질과 운영 문서까지 포함한다.
- URL 기준을 바꾸면 canonical, sitemap, robots, 분석 도구, Pages 설정을 한 세트로 점검해야 한다.
- 테스트는 현재 요구사항을 코드로 고정하지만, 테스트하지 않는 문제까지 찾아 주지는 않는다.
