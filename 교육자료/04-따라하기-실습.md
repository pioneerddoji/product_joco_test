# 04. 처음부터 따라 하는 실습

이 실습은 완성본을 복사하는 대신, 프로젝트가 발전한 순서를 축약해 직접 경험하도록 설계했습니다. 예상 시간은 2~3시간입니다.

## 준비물

- Git
- Node.js 20 이상 권장
- 코드 편집기
- 최신 브라우저
- 선택: GitHub 계정, Formspree/Disqus/Google/Microsoft 계정

외부 서비스 계정이 없어도 1~6단계까지 학습할 수 있습니다.

## 1단계 — 가장 작은 번호 생성기

`index.html`을 만들고 다음 요소를 둡니다.

- 제목과 설명
- `생성하기` 버튼
- 결과 영역
- 1~45 중 중복 없이 6개를 뽑는 함수
- 결과를 오름차순으로 보여 주는 코드

완료 조건:

- 매번 숫자가 6개 나온다.
- 모든 숫자가 1~45 범위다.
- 한 세트 안에 중복이 없다.
- 숫자가 오름차순이다.

생각 질문:

> 중복이 나오면 다시 뽑는 현재 방식과, 1~45 배열을 섞은 뒤 앞의 6개를 고르는 방식은 어떤 차이가 있을까?

## 2단계 — 표현과 동작 분리

인라인 스타일을 `styles.css`로, JavaScript를 `app.js`로 옮깁니다.

```html
<link rel="stylesheet" href="styles.css">
<script src="app.js"></script>
```

완료 조건:

- HTML만 읽어도 페이지 구조를 파악할 수 있다.
- CSS를 꺼도 번호 생성 기능은 남는다.
- JavaScript를 껐을 때 기능을 사용할 수 없다는 사실이 명확하다.

## 3단계 — 다크 모드

CSS 변수를 만들고 `data-theme`에 따라 값을 바꿉니다.

```css
:root {
  --page: #f5f7fb;
  --text: #202431;
}

:root[data-theme="dark"] {
  --page: #111526;
  --text: #f4f6fd;
}
```

JavaScript에서는 현재 테마를 토글하고 `localStorage`에 저장합니다.

완료 조건:

- 버튼을 누르면 즉시 바뀐다.
- 새로고침해도 선택이 유지된다.
- 버튼의 `aria-label`이 현재 동작을 설명한다.

## 4단계 — 콘텐츠 페이지 확장

다음 페이지를 최소 1개씩 작성합니다.

- 서비스 소개
- 사용 가이드
- 확률 또는 주제 학습
- 개인정보처리방침
- 이용약관

각 페이지에 고유한 title, description, canonical, `<main>`, `<nav>`, `<footer>`를 둡니다. 모든 내부 링크를 클릭해 404가 없는지 확인합니다.

## 5단계 — 검색 엔진 기본 설정

`robots.txt`와 `sitemap.xml`을 만듭니다. 여기서 먼저 배포 유형을 결정합니다.

| 유형 | 대표 주소 예시 |
|---|---|
| 사용자 사이트 | `https://name.github.io/` |
| 프로젝트 사이트 | `https://name.github.io/repository/` |

canonical, sitemap, robots의 주소가 같은 기준을 사용하는지 검색합니다.

```powershell
rg "https://name.github.io" .
```

완료 조건:

- sitemap에 공개 페이지가 모두 있다.
- robots가 sitemap을 가리킨다.
- 각 canonical이 실제 공개 주소와 일치한다.

## 6단계 — 가벼운 자동 검증

이 저장소의 `scripts/verify.mjs`를 읽고 다음 네 검사부터 직접 구현합니다.

1. 필수 HTML 파일이 존재한다.
2. title이 비어 있지 않고 서로 다르다.
3. 내부 링크 대상 파일이 존재한다.
4. 번호 생성 결과가 범위·중복·정렬 조건을 만족한다.

실행:

```powershell
node .\scripts\verify.mjs
```

실패 실습:

- 링크 하나를 존재하지 않는 파일로 바꾼다.
- title 두 개를 같게 만든다.
- 생성 범위를 46까지로 바꾼다.
- 검증이 실패하는지 확인한 뒤 원상 복구한다.

이 과정을 통해 테스트가 “코드가 맞는지 증명”하는 것이 아니라 “우리가 적어 둔 조건을 위반했는지 경고”한다는 점을 배웁니다.

## 7단계 — 외부 서비스 연결(선택)

한 번에 모두 연결하지 말고 하나씩 진행합니다.

### 문의 폼

1. Formspree 프로젝트를 만든다.
2. 폼 `action`을 연결한다.
3. 개인정보 동의와 스팸 방지 필드를 추가한다.
4. 배포 주소에서 테스트 문의를 보낸다.
5. 실제 수신과 회신 주소를 확인한다.

### 댓글

1. Disqus 사이트를 만든다.
2. shortname과 page identifier를 설정한다.
3. 로그아웃 상태, 모바일, 추적 차단 상태를 확인한다.
4. 운영 원칙과 개인정보 안내를 갱신한다.

### 분석·광고

1. 서비스별 프로젝트를 만든다.
2. 공개 가능한 측정 ID만 코드에 둔다.
3. 모든 공개 페이지에 중복 없이 들어갔는지 검사한다.
4. 개인정보처리방침을 갱신한다.
5. 실시간 또는 디버그 화면에서 데이터 유입을 확인한다.

## 8단계 — GitHub Pages 배포

```powershell
git status -sb
git add index.html styles.css app.js scripts/verify.mjs
git commit -m "Build number generator site"
git push
```

GitHub 저장소의 Settings → Pages에서 배포 브랜치와 경로를 선택합니다. 배포 후에는 다음을 확인합니다.

- 홈과 모든 내부 페이지의 HTTP 상태
- CSS와 JavaScript 로딩
- 번호 생성과 테마 유지
- 모바일 폭
- canonical과 실제 주소
- 최신 커밋이 Pages에 반영되었는지

## 최종 과제

다음 중 하나를 선택해 개선하고, 코드·정책·검증을 함께 수정합니다.

- 최근 생성한 세트를 브라우저에 저장하기
- 모든 HTML을 자동 탐색하는 검증 만들기
- 키보드와 스크린 리더 접근성 개선하기
- 외부 서비스가 차단되어도 이해 가능한 대체 UI 만들기
- GitHub Actions에서 `verify.mjs` 자동 실행하기

제출물에는 반드시 “무엇을 바꿨는가, 왜 바꿨는가, 어떻게 확인했는가”를 포함합니다.
